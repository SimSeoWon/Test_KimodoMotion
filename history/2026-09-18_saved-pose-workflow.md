# 포즈 프리셋을 저장된 포즈 작업 흐름으로 정리

- date: 2026-09-18
- status: implemented
- scope: 포즈 저장·불러오기, 후속 부분 수정

## 확인 결과

포즈 에디터의 AI 명령은 이미 현재 `PoseAsset` 전체를 서버에 보내고, 응답 전후를 비교해
실제로 달라진 컨트롤만 `changed_controls`에 기록한다. 그러나 UI와 HTTP 경로는 이를
"프리셋"이라고 불렀고, 저장 API는 클라이언트가 보낸 `revision`과 `edits`를 버렸다.
따라서 저장된 포즈를 다시 불러오면 형상은 유지돼도 그 포즈의 수정 계보는 끊겼다.

## 결정

사용자 개념은 별도 프리셋이 아니라 이름과 ID를 가진 저장 포즈다. UI는 "저장된 포즈"로
표현하고 기본 HTTP 경로를 `/api/poses`로 변경했다. 기존 로컬 클라이언트 호환을 위해
`/api/keypose-presets`는 같은 저장소를 가리키는 별칭으로만 유지한다.

저장과 로드 시 `controls`뿐 아니라 `id`, `revision`, `edits`도 보존한다. 이제 저장 포즈를
불러온 뒤 자연어 명령을 내리면 불러온 포즈가 기준이 되며, 에이전트는 전후 차이가 있는
컨트롤만 새 수정 이력으로 추가한다. 과거 `{name, controls}` 형식 파일은 revision 0의
포즈로 계속 읽는다.

## UI 소속 정리

AI 포즈 명령은 전체 포즈 작업공간의 독립 기능이 아니라 현재 편집 중인 임시 포즈에 대한
수정이다. 따라서 캔버스 위의 별도 패널을 제거하고, 캔버스 아래에서 포즈 이름과 저장
버튼이 있는 같은 작업 줄에 명령 입력과 `포즈 조절` 버튼을 배치했다. 수정 이력도 이 줄
바로 아래에 두어 어느 포즈에 귀속되는지 명확하게 했다.

## LLM 호출 정체 복구

포즈 에이전트는 별도 API 키가 아니라 로그인된 `claude.exe` CLI를 통해 원격 API를
호출한다. 단순 요청은 정상 응답했지만 한 포즈 요청이 CLI 내부에서 응답 없이 멎어 기존
단일 90초 제한에 도달했다. 일시적 정체를 복구할 수 있도록 50초 제한의 요청을 최대 두 번
시도한다. 두 번째 호출까지 멎으면 CLI 연결 상태를 명시한 오류를 반환하며 무한 대기하지
않는다.

## 상주 포즈 서브 에이전트

명령마다 `claude.exe`를 새로 실행하던 구조를 제거했다. WebUI 서버 시작 시 포즈 전용
CLI를 `stream-json` 입출력 모드로 한 번 시작하고 표준입력을 열어둔 채 대기시킨다. 이후
포즈 명령은 같은 프로세스에 사용자 턴으로 전달되므로 반복적인 CLI 초기화 비용이 없다.
서버 종료 시 프로세스도 함께 종료하며, 프로세스가 비정상 종료되거나 응답 제한을 넘기면
런타임이 새 프로세스를 한 번 기동해 요청을 복구한다.

## 2026-09-19 지연 진단

8188 포트에 WebUI Python 서버 두 개가 동시에 LISTEN 중이었고 각 서버가 별도의 상주
Claude 프로세스를 가지고 있었다. 브라우저의 명령 전송과 상태 폴링이 서로 다른 서버로
분산될 수 있어 `running` 상태가 오래 유지되고 재시도 프로세스도 중복됐다.

Windows에서 `SO_EXCLUSIVEADDRUSE`를 적용한 전용 HTTP 서버를 사용해 같은 포트의 두 번째
데몬 시작을 거부한다. 포즈 런타임은 최근 `init`, `api_retry`, `result` 이벤트와 프로세스
PID를 메모리에 보관하고 `/api/pose-agent/state`의 `runtime` 필드로 노출한다. 프롬프트나
응답 본문은 진단 로그에 넣지 않는다.
