# 로컬 웹 UI 추가 (Stable Diffusion WebUI 식)

## 배경

사용자가 "스테이블 디퓨전 웹UI처럼" 파라미터 입력 + 결과 미리보기를 하는 HTML/웹 UI를
요청. `kmd-generate.exe`를 직접 서버에서 호출해야 해서 Claude Artifact(샌드박스)가 아니라
로컬 앱으로 만들기로 함.

## 만든 것

`webui/` 신설 (git에 커밋, 외부 의존성 없음 — Python 표준 라이브러리만):

- `server.py` — `http.server.ThreadingHTTPServer` 기반. `kmd-generate.exe` → `export_glb.py`를
  `generate-motion.ps1`과 같은 방식(같은 PATH/`KIMODO_BACKEND` 처리)으로 그대로 서브프로세스
  호출. 라우트: `GET /`, `GET /static/*`, `GET /outputs/<gen_id>/animation.glb`,
  `GET /api/status`, `GET /api/history`, `POST /api/generate`.
  - 동시 생성 요청은 `threading.Lock`으로 직렬화(GPU 하나이므로 2개 이상 동시 실행 방지).
  - `UnrealEditor` 프로세스 감지(`tasklist` 파싱) + Vulkan 백엔드 조합이면 프런트에서 경고
    배너 표시(자동 차단은 안 함 — `generate-motion.ps1`과 같은 정책, HTTP라 인터랙티브
    확인이 불가능해서 배너로 대체).
  - 결과는 `output_motion/generations/<타임스탬프>_<슬러그>/`에 `animation.glb` +
    `meta.json`(prompt/frame_count/steps/seed/backend/model/text_bundle/elapsed_sec)으로 저장.
    `output_motion/`이 이미 `.gitignore` 대상이라 서브디렉터리도 자동으로 걸림.
- `static/index.html`, `app.js`, `style.css` — 다크 테마. 왼쪽: prompt, frame count/steps
  (슬라이더+숫자 동기화), seed(🎲 랜덤 버튼), backend, 고급 옵션(모델 경로/텍스트 번들
  경로 — 기본값은 README와 동일). 오른쪽: `<model-viewer>`(CDN, `@google/model-viewer@3.5.0`)
  로 glb 애니메이션 바로 재생 + 다운로드 링크. 하단: 히스토리 카드 목록, 클릭하면 파라미터와
  결과를 그대로 복원.

## 검증

실제 파이프라인으로 end-to-end 테스트: `POST /api/generate`
`{"prompt":"a person waving hello","frame_count":30,"steps":10,"seed":1,"backend":"vulkan"}`
→ 20.3초 만에 `animation.glb`(38KB) 생성 확인, `GET /outputs/.../animation.glb` 200 확인,
히스토리 목록 반영 확인. 테스트로 만든 산출물과 서버 프로세스는 세션 중에 정리함.

## 실행

```powershell
py webui\server.py   # http://127.0.0.1:8188/
```

## "엔비디아 막시모" 논의 — 실제로는 "미리보기에 보여줄 사람 메시가 없다"는 뜻이었음

사용자가 고급 옵션(모델 경로/텍스트 번들 경로)을 보고 "엔비디아 막시모를 베이스로 키모도가
작성하게 해볼까"라고 제안. 조사해보니 kimodo.cpp의 `download_gguf_weights.py` `MODEL_MAP`에는
`soma-rp-v1.1`/`soma-seed-v1.1`/`g1-rp-v1`/`g1-seed-v1`만 있고 "Maximo"라는 NVIDIA 모델은
없음 — 사용자에게 확인하니 **Adobe Mixamo와 혼동**한 게 아니라(그건 Mixamo(믹사모)가 뭔지
맞다고 답함), "kimodo가 Mixamo 캐릭터를 베이스로 생성하게" 하자는 뜻이 아니라 **"웹 UX에
보여줄 (사람) 모델이 없다"** — 즉 `export_glb.py`가 만드는 게 관절마다 작은 큐브뿐이라
미리보기에 사람이 안 보인다는 지적이었음. Mixamo는 그 메시를 구할 소스로 거론한 것.

두 방향(1. Mixamo FBX를 실제로 받아서 SOMA30에 스키닝 바인딩 — Blender 미설치라 큰 작업,
2. 큐브 대신 캡슐로만 바꿔서 사람 실루엣 근사 — 새 의존성 없이 바로 적용)을 제시했고
사용자가 **2번(캡슐 스타일)** 선택.

## 만든 것 (2) — `scripts/pretty_export_glb.py`

vendor의 `export_glb.py`(핀 고정 서브모듈, 손 안 댐)를 import해서 `create_bone_mesh()`만
몽키패치. 관절마다:
- 루트(Hips, parent=-1)는 그 자리에 구 근사 블롭(자기 자신에게 캡슐, 길이 0 → 캡)
- 나머지는 부모→자신을 잇는 8각 저폴리 캡슐(원기둥 옆면 + 원뿔형 캡 2개)
- 반지름은 soma30 조인트 순서(0=Hips..29=RightToeBase, vendor `SKELETONS["soma30"]["names"]`와
  같은 순서) 기준 하드코딩 표 `_RADII` — `create_bone_mesh(global_pos, parents)` 시그니처가
  이름을 안 받아서 인덱스로 고정(다른 스켈레톤 추가되면 표도 늘려야 함, 지금은 soma30뿐).
- 모든 정점은 자기 조인트에 100% 강체 스키닝(원본과 같은 방식, 부드러운 블렌딩 없음).
- 쓰고 난 뒤 glb를 다시 열어 `doubleSided: true` 재질을 하나 추가(JSON 청크만 재작성, BIN은
  바이트 그대로 재사용) — 캡슐 옆면 삼각형 감김 방향을 대수적으로 유도해서 맞췄다고 보지만
  실제 GPU 렌더러로 직접 눈으로 확인은 못 했으니, 방향이 어느 한쪽에서 틀려도 안 보이는 면이
  안 생기게 하는 안전장치.

**웹 UI 전용** — `generate-motion.ps1`/README의 UE5 임포트 경로는 그대로 vendor의
`export_glb.py`를 쓴다(그쪽은 SOMA 메시를 안 쓰고 IK Retargeter로 UE 마네킹 메시로 바로
갈아치우므로 SOMA 쪽 메시 모양은 안 중요함). `webui/server.py`의 `EXPORT_GLB_PY`가 이 새
스크립트를 가리키도록 바꿈.

**검증**: 기존 `output_motion/`의 raw .f32로 직접 실행 → glb 파싱해서 vertex 540개
(30조인트×18정점), index 2880개, 전부 인덱스 범위 내, NaN 없음, material에 `doubleSided:true`
확인. 사람 크기에 맞는 바운딩 박스(폭 ~1.86m, 키 ~1.69m)도 확인. 웹 UI `/api/generate`를
통해서도 같은 결과 나오는 것까지 end-to-end로 재확인, 테스트 산출물 정리함.

## 만든 것 (3) — 같은 세션에서 바로 Mixamo 경로도 진행함

사용자가 캡슐 스타일 확인 후 "그럼 믹시모에서 모델을 받아와서 어디에 넣어주면 되는거야?"라고
물어서, 캡슐로 끝내지 않고 실제 Mixamo 캐릭터 메시 바인딩까지 진행함.

1. Mixamo에서 **Y Bot.fbx**(With Skin, 기본 T-pose)를 사용자가 받음 → `assets/mixamo_src/`로
   이동(다운로드 폴더에서 자동 탐색해서 옮김). `.gitignore`에
   `assets/mixamo_src/`/`assets/mixamo_processed/` 추가(Mixamo 재배포 금지 라이선스).
2. `pip install bpy`는 이 Python(3.12)용 휠이 없어서 실패 — **Blender 5.2.1을 winget으로
   설치**(`BlenderFoundation.Blender`, 사용자 승인받고 진행). `blender.exe`는
   `C:\Program Files\Blender Foundation\Blender 5.2\blender.exe`.
3. `assets/_inspect_mixamo.py`로 Y Bot의 실제 본 계층/vertex group 이름을 먼저 덤프해서
   확인(추측 안 함 — 프로젝트 방법론 그대로). 발견한 것:
   - 메시 오브젝트가 2개(`Alpha_Surface`=진짜 스킨, `Alpha_Joints`=장식용 관절 마커) —
     처음에 `Alpha_Joints`를 잘못 골랐다가 vertex group이 이상해서(Head 그룹 없음 등)
     `Alpha_Surface`로 바로잡음.
   - Mixamo 본 이름이 SOMA30과 **부분적으로만** 일치(어깨/팔 체인은 이름까지 똑같음).
     다리는 이름이 반대로 꼬여 있음: SOMA `LeftLeg`=허벅지인데 Mixamo `LeftUpLeg`=허벅지,
     Mixamo `LeftLeg`=정강이(SOMA `LeftShin`에 해당) — 이름만 보고 매칭했으면 다리가
     한 단계씩 밀렸을 뻔함.
   - Mixamo 표준 리그엔 목(Neck1/Neck2 둘로 안 나뉨, Neck 하나뿐)/턱/눈 본이 없음 → SOMA
     Neck1/Neck2/Jaw/LeftEye/RightEye 5개는 Mixamo 메시로 못 채움(캡슐로 폴백).
   - 손가락은 Mixamo가 손가락당 3본(끝마디 제외)까지 웨이트가 있는데 SOMA는 손당 마커 2개
     (`*HandThumbEnd`/`*HandMiddleEnd`)뿐 — 엄지 체인은 ThumbEnd로, 나머지 네 손가락은
     MiddleEnd로 뭉뚱그림.
   - 단위: Mixamo 본좌표 raw 값은 cm 스케일(Hips y≈99.8)인데, Blender의 `matrix_world`를
     거쳐서 뽑으면 자동으로 미터로 맞춰짐(따로 /100 안 해도 됨) — 실측으로 확인(최종 bbox가
     사람 크기로 나옴).
4. `assets/extract_mixamo_soma30.py` 작성 — 정점마다 가장 가중치 높은 Mixamo vertex
   group을 찾아서: (그 본의 월드 head 기준 로컬 오프셋) + (SOMA30 레스트 글로벌 위치)로
   최종 좌표를 만듦 — "로컬 디테일은 유지, 관절 피벗만 SOMA30 배치로 이동". 단순히 Mixamo
   원본 좌표를 그대로 쓰지 않은 이유: `export_glb.py`의 역바인드행렬이 SOMA30 rest 위치로만
   계산되므로, 애니메이션(회전)이 시작되면 정점이 실제로 어느 조인트에 얼마나 가까운지가
   왜곡의 크기를 결정함 — 로컬 오프셋을 보존해야 관절이 돌 때 자연스럽게 따라감.
   실행 결과: 정점 17336개, 전부 매핑됨(스킵 0), bbox 폭 1.9m/키 1.79m로 사람 크기 확인.
5. `scripts/pretty_export_glb.py`를 확장 — `assets/mixamo_processed/ybot_soma30_bind.json`이
   있으면 그 메시를 쓰고, 없는 조인트(위 5개) 또는 파일 자체가 없으면 캡슐로 채우는
   `create_preview_mesh()`로 교체. 바인딩 파일이 없어도(다른 사람이 리포 클론했을 때 등)
   캡슐 폴백으로 그냥 동작함.

**검증**: `output_motion/`의 raw 모션으로 직접 실행 → 정점 17426개(17336+캡슐90), 인덱스
103920개, 조인트 0~29 전부 사용 확인, bbox 사람 크기, NaN 없음. 웹 UI
`POST /api/generate`(`"a person jumping happily"`)로 end-to-end 재확인, glb 서빙 200 확인.
이번엔 이 결과물을 히스토리에 남겨둠(다음에 브라우저로 바로 열어볼 수 있게) — 나머지 테스트
산출물/서버 프로세스는 정리함.

## 버그: Blender Z-up vs glTF/SOMA30 Y-up 축 불일치 (같은 세션에서 발견·수정)

사용자가 실제로 웹 UI를 열어서 "다 이상하게 나온다", "얼굴, 목, 종아리, 발목 싹다 기괴하게
엉켜있어"라고 보고함. Claude가 직접 눈으로 본 적 없이 구조적 검증(NaN/인덱스 범위/bbox)만
했던 게 문제 — 구조는 멀쩡해도 좌표축이 틀리면 저런 검증으론 안 잡힘.

**진단 방법**: Blender headless로 문제의 glb를 직접 임포트해서 카메라+라이트 세팅하고
`bpy.ops.render.render`로 PNG를 렌더 → Read 도구로 이미지를 직접 봄. 벤더 원본
큐브-메시 버전도 같은 프레임으로 렌더해서 비교 — 큐브 버전은 정상적인 사람 실루엣으로
나와서, 스켈레톤/애니메이션 데이터 자체는 문제없고 **Mixamo 메시 바인딩 쪽 버그**라고
바로 좁혀짐(원인 조사에 결정적이었음 — 이후 세션에서도 "렌더해서 직접 비교" 패턴을
재사용할 만함).

**원인**: `assets/extract_mixamo_soma30.py`가 Blender의 `bone.head_local`/`v.co`(Blender
네이티브 좌표계, **Z-up**)를 축 변환 없이 그대로 SOMA30 오프셋(glTF 컨벤션, **Y-up**)에
더했음. 회전이 없는 레스트 프레임에서는 이 문제가 안 보임(항등 변환이라 정점 좌표가
그대로 나옴 — 그래서 처음 구조 검증 때 bbox가 "사람 크기"로 그럴듯하게 나온 것도 우연히
안 걸림). 실제 애니메이션 회전이 걸리는 순간 로컬 오프셋의 축이 뒤집혀서 팔다리가 엉뚱한
방향으로 꺾이고, 체인을 타고 내려갈수록(허벅지→종아리→발) 왜곡이 누적됨 — 사용자가 본
"엉켜있다"는 정확히 이 증상.

**수정**: `to_gltf_up(v) = (v.x, v.z, -v.y)`(Blender의 glTF 익스포터가 쓰는 "+Y Up" 표준
변환과 동일)를 `bone_head_world`와 정점 월드 좌표 양쪽에 적용. `assets/mixamo_processed/
ybot_soma30_bind.json` 재생성 후 Blender 렌더로 재확인 — 서 있는 사람 실루엣, 팔다리
굽힘도 자연스러움(엄지/검지 뭉친 손가락 블롭이 손 옆에 살짝 떨어져 보이는 정도의 사소한
디테일만 남음). 저장해둔 히스토리 예시(`20260915-161212_a-person-jumping-happily`)의
glb도 고쳐진 걸로 다시 내보내서 갱신함.

## 재질 색상 — Y Bot 고유 청록색 반영

축 버그 고친 뒤 사용자가 "잘 나오는거 같은데, 믹시모 캐릭터는 아닌가봐?"라고 확인 —
모양은 맞는데 임의로 넣은 살구색 때문에 Mixamo 캐릭터처럼 안 보인다는 지적.

확인해보니 Y Bot.fbx엔 텍스처 이미지가 전혀 없다(Blender로 머티리얼 노드 덤프 — 임베드된
이미지 0개). 대신 Principled BSDF의 Base Color가 평평한 청록색 `(0.0966, 0.4216, 0.5220,
1.0)` — 이게 Y Bot 특유의 그 색. `extract_mixamo_soma30.py`가 이 값을 읽어서 바인딩
JSON의 `base_color`로 같이 저장하게 하고, `pretty_export_glb.py`의
`_make_double_sided_skin_material()`이 그 색을 재질에 쓰도록 수정(없으면 기존 살구색
폴백 유지). Blender 렌더로 청록색이 제대로 나오는 것까지 확인, 저장해둔 히스토리 예시도
다시 내보내서 갱신함.

## 재설계 — 이음매 갈라짐 + 손가락 뭉침 (사용자가 렌더 보고 구체적으로 지적)

색 고친 뒤 사용자가 "생긴게 다른데?"라고 재차 지적. Claude가 렌더 이미지를 다시 보니
어깨/허리/허벅지 경계마다 메시가 갈라져 떠 보임 — 처음엔 "Y Bot 원래 그런 로봇 디자인
아니냐"고 오판해서 사용자에게 확인 질문을 시도했으나(AskUserQuestion 인자 실수로 실패),
사용자가 먼저 구체적으로 지적함: **"믹스모 리소스 쓰는거 맞냐, 그 리소스에선 손가락도
5개고 지금처럼 견갑골이 위로 떠있지도 않고, 틈 사이에도 구형 메시가 있다"**.

두 가지 진짜 원인을 찾음:

1. **재배치(recenter) 방식 자체가 이음매를 만듦**: 첫 설계는 "정점 - 자기 본 head + SOMA30
   레스트 위치"로 정점을 옮기는 방식이었는데, SOMA30과 Mixamo Y Bot의 실제 본 길이가
   정확히 같지 않아서, 서로 다른 본에 묶인 두 정점(예: 가슴은 Chest에, 위팔은 LeftArm에)이
   각자 다른 양만큼 밀려 관절 경계마다 메시가 갈라짐 — **회전 없는 레스트 프레임에서도**
   나타나는 문제였음(축 버그와 별개). 손가락도 이 방식 때문에 여러 손가락이 SOMA의 단일
   마커(ThumbEnd/MiddleEnd) 위치로 다 같이 재배치되면서 한 점으로 뭉쳤음.
2. **`Alpha_Joints` 메시를 처음부터 빼먹음**: Y Bot은 메시가 2개 — `Alpha_Surface`(갑옷
   판)와 `Alpha_Joints`(그 판 사이 틈을 메우는 구형 관절 메시). 첫 버전에서 `Alpha_Surface`
   만 쓰기로 판단할 때 `Alpha_Joints`를 "장식용"이라고 잘못 추측하고 버렸는데, 실제로는
   갑옷 판들을 안 갈라져 보이게 이어주는 필수 부품이었음.

**재설계**: `extract_mixamo_soma30.py`를 다시 짬 —
- SOMA30의 조인트 계층(이름·부모·30개 순서)은 그대로 두되, **각 본의 offsets(부모 대비
  로컬 위치)를 Mixamo 자신의 실제 치수로 통째로 교체**(27/30개 조인트를 Mixamo 본 위치로
  덮어씀 — Jaw/LeftEye/RightEye 3개만 Mixamo에 대응이 없어서 SOMA30 원본 유지). 목은
  Mixamo에 `Neck` 하나뿐이라 Neck1=Neck.head, Neck2=Neck~Head 60% 보간으로 근사.
- 메시 정점은 이제 **재배치 없이 Mixamo 원본 좌표를 그대로 씀** — 스켈레톤을 메시에 맞춰
  놨으니(반대가 아니라) 이음매 계산이 아예 필요 없어짐. 손가락도 재배치 안 하니 Hand에
  자연스럽게 붙어서 5개가 갈라져 보임.
- `Alpha_Surface`(17336정점) + `Alpha_Joints`(10514정점)를 합쳐서 하나의 메시로 출력
  (총 27850정점, 인덱스 165960 — uint16 한도 65536 안쪽).
- `pretty_export_glb.py`는 이제 `convert_motion_to_glb` 호출 전에
  `export_glb.SKELETONS["soma30"]["offsets"]`를 바인딩 JSON의 `offsets`로 덮어씀(이 모듈은
  프로세스 안에서만 한 번 몽키패치되니 vendor 파일 자체는 안 건드림).

**검증**: Blender 렌더로 재확인 — 어깨/목/허리/골반/무릎 전부 구형 관절로 이어져서 붕
뜬 부분 없음, 손도 프레임 15(팔을 들어올린 포즈)에서 손가락 5개가 뚜렷하게 갈라져 보임
(프레임 0은 팔을 내린 자세라 손이 엉덩이 옆에 있어서 잠깐 헷갈렸을 뿐). 저장해둔 히스토리
예시도 다시 내보내서 갱신함.

## 버그: 손가락이 애니메이션 중 화면 밖으로 날아감

이음매/Alpha_Joints 수정 뒤 사용자가 "손가락 아직도 망가져있어"라고 재차 지적. 프레임
0/15만 렌더해서 괜찮아 보였는데, 프레임 3/8/20/29를 추가로 렌더해보니 엄지 아닌 네 손가락
(조인트 15=MiddleEnd로 뭉친 것)이 손목에서 대각선으로 멀리 떨어져 나가 있었음(0/15는
우연히 덜 튀는 각도였을 뿐).

**원인**: SOMA30의 `*HandThumbEnd`/`*HandMiddleEnd`는 진짜 손가락 관절이 아니라 이름만
있는 리프 마커 — 모델이 그 마커에 주는 회전값은 실제 손가락 기하와 무관한(사실상 의미
없는) 값인데, 재배치 없이 원본 좌표를 그대로 그 마커 조인트에 묶어놨으니, 그 조인트가
조금만 회전해도 마커 위치(global_rest[15])에서 먼 정점(실제 손가락들)이 지렛대처럼 크게
휘둘려 날아감 — 회전 없는 레스트 프레임에서는 항등변환이라 안 보이는 부류의 문제라
프레임을 몇 개만 보고 넘어가면 놓치기 쉬움.

**수정**: 손가락 정점(Thumb/Index/Middle/Ring/Pinky 전부)을 마커(14/15/20/21) 대신
**손(Hand, 13/19) 자체에 강체로** 묶음 — SOMA30엔 애초에 손가락 개별 자유도가 없으니
잃을 게 없고, Hand는 이미 Mixamo 치수 기준으로 정확히 배치돼 있어서 손이 움직이는 대로
손가락도 자연스럽게 같이 움직임. 6개 프레임(0/3/8/15/20/29) 렌더로 전부 확인 — 모든
프레임에서 손가락이 손목에 붙어 있음.

## 재질 분리 — 갑옷 판(청록) vs 관절 구(어두운 메탈릭 회색)

손가락 고친 뒤 사용자가 "조인트는 검은색인가봐"라고 언급. 처음엔 렌더로 재현되는 어두운
영역을 "법선(NORMAL)이 없어서 뷰어가 잘못 계산하는 것"이라고 오판해서 `_add_smooth_normals`
후처리를 먼저 추가했는데(스펙 준수 차원에서는 맞는 방향이라 그대로 둠), EEVEE로 다시
렌더해보니 그 특정 어두운 부분은 그냥 단일 광원 테스트 환경의 자연스러운 그림자였고
진짜 원인이 아니었음.

Blender로 `Alpha_Joints_MAT`를 직접 확인하니 실제로 어두운 메탈릭 회색(RGB≈0.15, 0.21,
0.22, Metallic=0.5)이었음 — **사용자 말이 맞았다**: Y Bot은 갑옷 판(Alpha_Surface, 청록)과
관절 구(Alpha_Joints, 어두운 회색)의 재질이 실제로 다른데, 지금까지 메시 전체를 재질
하나(청록)로 뭉개서 관절도 청록색으로 나왔던 것.

**수정**: `extract_mixamo_soma30.py`가 이제 두 메시 각각의 실제 Base Color를 뽑아서
정점마다 `colors`로 들고 감. `pretty_export_glb.py`에 `_add_vertex_colors()`(COLOR_0
주입) 추가하고, COLOR_0이 있으면 재질의 baseColorFactor를 흰색으로 둠(glTF는 COLOR_0×
baseColorFactor로 곱해지므로 이중으로 곱해지면 색이 틀어짐 — `create_bone_mesh()`의
고정 반환 시그니처엔 색을 못 넣어서 모듈 전역 `_last_vertex_colors`를 사이드채널로 씀).
EEVEE 렌더로 확인 — 목/허리/골반/무릎/발목 이음매 틈으로 어두운 회색 관절 구가 청록
갑옷과 대비되어 제대로 보임.

**사용자 최종 확인(2026-09-16): "좋아 잘 나와!"** — 손 부착, 이음매, 관절 재질 색까지
전부 확인 완료.

## 다음 세션에서 할 일

- 사용자에게 웹 UI에서 다시 확인받기(브라우저 캐시 때문에 같은 glb URL이면 강제 새로고침
  필요할 수 있음).
- 목/턱/눈(SOMA30 원본 오프셋 + 캡슐 폴백 3개 조인트만 남음, Neck1/Neck2는 이번에
  Mixamo 근사로 편입됨)은 Alpha_Surface 색(청록)으로 채워짐 — 실제로 안 튀는지 확인.
- **방법론 메모(중요, 세 번 겪음)**: 프레임 1~2개만 렌더하고 "괜찮아 보인다"고 판단하면
  안 됨(축 버그·손가락 버그 둘 다 이 패턴) — **최소 5~6개 프레임을 고르게 렌더**할 것.
  또 Blender의 렌더 엔진에 따라 결과가 다르다는 것도 이번에 배움 —
  **BLENDER_WORKBENCH(색 모드 MATERIAL)는 정점 색(COLOR_0)을 못 보여준다, 재질/조명
  관련 확인은 BLENDER_EEVEE로 렌더할 것.** 그리고 이상해 보이는 결과를 "이게 원래
  디자인이겠거니"도, "이게 버그겠거니"도 넘겨짚지 말고 근거(재질 노드를 직접 덤프하는 등)
  를 확인한 뒤 판단할 것 — 사용자가 실제 리소스를 아는 경우가 많다.
